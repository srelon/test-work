# CLAUDE.md (backend)

Backend-specific conventions for `backend/` (Laravel 12, API only). See the root `CLAUDE.md` for Docker/monorepo-wide rules, `frontend/CLAUDE.md` for the Vue app.

## Current state

Still only the framework itself + `predis/predis` + `php-amqplib/php-amqplib` in `composer.json` — no Sanctum. `QUEUE_CONNECTION=redis` **is** actually in use, as the fallback/retry path for comment persistence when RabbitMQ can't be used directly, rather than RabbitMQ being wired up as a Laravel queue driver itself — see § Queue (RabbitMQ, with a Laravel-job fallback/retry path). Don't reference packages that aren't in `composer.json` — check before assuming something (Sanctum, a specific cache/queue driver) is available.

`routes/api.php` now exists and is registered via `api:` in `bootstrap/app.php`'s `withRouting(...)`. First (and so far only) resource: `comments` — `Comment` model + migration (self-referencing `parent_id`, plus a bare `replied_to_comment_id` with no FK, matching the reference's threaded-reply pattern), `CommentController` (`index`/`store`/`replies` — no `update`/`destroy`, since comments are anonymous/guest with no auth to gate ownership), `CommentService`, `CommentResource`, `CommentRequest` + `CommentFilterRequest` (validates/defaults `sort_by`). `App\Http\Controllers\Controller` now `use`s `App\Traits\RespondTrait` (ported from the reference) — every controller response goes through `respondWithJson`/`respondWithError`, never a hand-built array.

**`user_name`/`email` are not columns on `comments` — they live on a separate `contacts` table, deduplicated by the (`email`, `user_name`) pair, and are reached via `Comment::contact()` (`belongsTo`).** `CommentService::persist()` resolves the contact with `Contact::firstOrCreate(['email' => ..., 'user_name' => ...])` before creating the comment (this is the actual dedup point — the same pair reuses the same row instead of writing a fresh one every time), so `comments.contact_id` is the only place identity is stored. `Comment` exposes `user_name`/`email` back out as read-only `Attribute` accessors that proxy to `$this->contact` — this is why `CommentResource`, `CommentCreated::broadcastWith()`, and the sort-by-name/email `CommentFilterRequest` options didn't need to change shape; only the storage moved, not the API contract. Because those accessors touch the `contact` relation, every query that resolves a `CommentResource` (`CommentService::getPaginated()`, `getReplies()`) eager-loads `contact` (and `repliedTo.contact` where relevant) to avoid an N+1 — don't add a new comment-fetching code path without doing the same. Sorting by `user_name`/`email` (`CommentFilterRequest`'s `user_name_asc`/`email_asc`/etc.) can no longer `orderBy()` a `comments` column directly — `CommentService::orderByContactColumn()` joins `contacts` and orders on that instead. Split across two migrations, so the schema-only step can land ahead of the data move: `2026_08_21_000001_create_contacts_table` just creates the table; `2026_08_21_000002_migrate_comments_to_contacts` adds `comments.contact_id`, backfills every existing `(email, user_name)` pair into `contacts` on `up()`, and reverses that (rebuilding `user_name`/`email` on `comments` from the `contacts` join, then dropping `contact_id`) on `down()` — both directions are real, tested migrations, not one-way. `comments.contact_id` (and, on rollback, `user_name`/`email`) still ends up `NOT NULL` on real MySQL, but the migration can't get there through `Schema::table()->change()` — that needs `doctrine/dbal`, not installed here — so it's a driver-gated raw `DB::statement('ALTER TABLE ... MODIFY ...')`, skipped when `DB::connection()->getDriverName() !== 'mysql'`. That gate exists specifically for the test suite, which runs against sqlite (`phpunit.xml`) where `ALTER TABLE ... MODIFY` isn't valid syntax at all — sqlite tests get a nullable column at the schema level, but the app still always populates it (`Contact::firstOrCreate()` in `persist()`), so nothing behavioral depends on the constraint being enforced there.

`down()` ends with `DB::table('contacts')->truncate()` — found the hard way by actually rolling back and re-running this migration by itself (`migrate:rollback --step=1`, not the full `--step=2` that also undoes `2026_08_21_000001_create_contacts_table`'s own `Schema::dropIfExists('contacts')`). Without the truncate, the rows this migration's `up()` backfilled into `contacts` survive the rollback (that table is owned by the *other* migration), so re-running `up()` immediately hits the `(email, user_name)` unique constraint on rows that already exist. `down()` copies the data back out to `comments` first, then clears `contacts` — since it's the one that put those rows there, it's the one responsible for removing them.

**Replies are not eager-loaded with the top-level comment list.** `CommentService::getPaginated()` uses `withCount('replies')`, not `->with('replies')` — `index` only ever returns each top-level comment's `replies_count`, never the nested records. The actual replies for one specific comment come from a separate endpoint, `GET comments/{comment}/replies` (route-model-bound, `abort_if($comment->parent_id !== null, 404)` — you can't fetch "replies of a reply", matching the one-level-deep thread design), backed by `CommentService::getReplies(Comment $comment)`. `CommentResource::toArray()` only ever exposes `replies_count` (`$this->resource->replies_count ?? 0` when `parent_id === null`, else `0`) — there is no `'replies'` key in the resource at all anymore, on any endpoint. This split (count eagerly, records on demand) matches `demo-news`'s own `CommentService`/`CommentController` pattern for the same problem.

**Guest-submitted image uploads (base64 data URLs) go through `App\Traits\SavesBase64Images`** (alongside `App\Traits\RespondTrait` — this is where all cross-cutting traits live, not a per-namespace `Concerns` folder). Never trust the client's declared MIME type or file extension — decode via GD's `imagecreatefromstring()` and reject (`ValidationException`) anything that fails to decode as a real image, then always re-encode to a fresh PNG before storing (strips any non-image payload disguised with a fake `data:image/png;base64,` prefix, e.g. a PHP webshell). Uses plain `php-gd` (already in `_docker/app/Dockerfile`), not Imagick — Imagick isn't installed here or in the reference, and adding it means a Dockerfile/image-rebuild change; ask before reaching for it. `saveBase64ImageFit(...)` scales down only if over given max dimensions (never upscales, preserves aspect ratio); `saveBase64ImageCover(...)` resizes to an exact target size (may distort if the source aspect ratio differs — there is no crop-to-avoid-distortion step, that was deliberately simplified away, see [[feedback-reuse-reference-patterns]]).

**HTML sanitization for user-submitted rich text is a strict tag whitelist (`a`, `code`, `i`, `strong`) enforced on the backend** (`CommentService::sanitizeBody()`, plain `strip_tags()` + regex, not `DOMDocument` — kept intentionally simple, see [[feedback-reuse-reference-patterns]]) **and mirrored on the frontend** (`utils/sanitizeCommentHtml.ts`) for defense in depth. If the allowed tag set ever changes, update both sides together — they're independent implementations of the same whitelist, not shared code. `<a>` gets `rel="nofollow noindex"` force-injected server-side regardless of what the client sent. Regex tag-matching for `<p>` must use a lookahead (`(?=[\s>\/])`) after the tag name — a naive `<\/?p[^>]*>` also matches `<pre>`/`</pre>` since `[^>]*` swallows the "re".

## Architecture conventions — apply these as real endpoints get built

**Validation lives in Form Requests, never in controllers.** One request class per resource, shared between create and update — read the route's id param inside `rules()` to adjust (e.g. `Rule::unique(...)->ignore($id)` for edit vs. plain `unique` for create).

```php
class ProductRequest extends FormRequest
{
    public function rules(): array
    {
        $id = $this->route('id');
        return [
            'title' => ['required', 'string', 'max:255'],
            'slug' => ['required', 'string', Rule::unique('products', 'slug')->ignore($id)],
        ];
    }
}
```

**No business logic in controllers.** A controller method only resolves a Request, calls a Service (`app/Services/`), and returns the response.

**Before creating a new one-off Service class, check whether an existing service already owns that domain and just add a method** — don't default to a new top-level Service/Controller per endpoint when one already covers that resource area.

**Response array shape belongs in `app/Http/Resources/`, not inline in a service method.** Every model→array transformation should be a `JsonResource`. One resource class per model/domain, not one per shape variant — a boolean constructor flag (e.g. `ProductResource(Product $product, bool $detailed = false)`) can cover both a list-card shape and a full-detail shape instead of splitting into separate files.

**Group routes by resource, don't declare flat separate `Route::` calls.** One `Route::prefix('resource')->controller(Controller::class)->group(function () { ... })` block per resource area.

## Rate limiting

Uses Laravel's built-in `throttle` route middleware (backed by the cache — the app's *default* store, `CACHE_STORE=database`, not Redis; see § Caching for why the default was moved off Redis) — no separate package. Keyed by IP by default (`ThrottleRequests::resolveRequestSignature()` falls back to `$request->ip()` since there's no auth/user in this project), bucketed separately per route (`GET comments`, `POST comments`, `GET comments/{id}/replies` each get their own counter, not a shared one). `routes/api.php`: `POST comments` is `throttle:10,1` (10/min — the actual spam vector, since it now always returns `202` fast, per § Queue), the two `GET` routes are `throttle:60,1` (generous — normal browsing shouldn't hit it, a scripted flood should).

**The default `ThrottleRequestsException` response doesn't match this project's `RespondTrait` envelope** (`{"data": ..., "status": ...}` / `{"status": ..., "errors": ...}`) — Laravel's own renders as a bare `{"message": "..."}`. `bootstrap/app.php`'s `withExceptions()` registers a `render()` callback specifically for `ThrottleRequestsException` on `api/*` routes, rebuilding the same `{"status": 429, "errors": "..."}` shape `RespondTrait::respondWithError()` produces — done inline in the closure (not by calling into the trait, which needs a controller instance) since this is the one place outside a controller a response gets built. `$e->getHeaders()` is passed through so `Retry-After`/`X-RateLimit-*` still reach the client.

## reCAPTCHA

`POST comments` requires a `recaptcha_token` field (Google reCAPTCHA **v2 Checkbox** — the "I'm not a robot" widget, always visible, not the invisible/score-based variants), validated server-side in `CommentRequest::rules()` via a closure calling `App\Services\RecaptchaService::verify(string $token, ?string $ip): bool`. That service POSTs the token + `services.recaptcha.secret_key` (env `RECAPTCHA_SECRET_KEY`) to Google's `siteverify` endpoint using Laravel's `Http` facade and returns the raw `success` boolean — **no fallback/resilience layer here, unlike Redis/RabbitMQ**: this is a third-party anti-spam check, not this app's own infrastructure, so if the HTTP call itself throws (network blip, Google down), `verify()` catches it and returns `false` — failing *closed* (reject the comment) rather than *open* (let it through unchecked), the opposite tradeoff from everything in § Caching/§ Queue, deliberately, since silently bypassing a spam check on a transient error defeats its purpose.

**HTTPS is not required for local development, despite what the reCAPTCHA admin console might imply** — domain registration for a site+secret key pair only checks the hostname (no port, no protocol, no DNS ownership verification), and Google automatically permits `localhost` for any key regardless of whether it's in the registered domain list. This project's `.env`/`.env.example` (both backend `RECAPTCHA_SECRET_KEY` and frontend `VITE_RECAPTCHA_SITE_KEY`) ship with **Google's official always-pass test key pair** (site `6LeIxAcTAAAAAJcZVRqyHh71UMIEGNQ_MXjiZKhI` / secret `6LeIxAcTAAAAAGG-vFI1TnRWxMZNFuojJ4WifJWe`, documented by Google specifically for this purpose) — the checkbox widget renders normally but `siteverify` always reports `success: true` regardless of input, so this only proves the integration wires up correctly, not that it actually blocks anything. Swap in a real registered key pair (with `localhost`/`127.0.0.1` added to its domain list) to test the real pass/fail behavior.

**The test *secret* key is what makes verification always pass — it isn't cross-checked against which site key produced the token.** Swapping only the frontend's `VITE_RECAPTCHA_SITE_KEY` to a real registered key while leaving the backend on the test `RECAPTCHA_SECRET_KEY` still returns `success: true` for *any* token, including a garbage string typed by hand — the test secret doesn't verify the token against Google's real challenge state at all, it's a hardcoded stub keyed off the secret value itself. Both halves of the pair need to be swapped together for verification to mean anything; there's no way to test "does mismatched site/secret get rejected" using either official test key, since the test secret bypasses that check entirely. Confirmed live: real secret + a hand-typed bogus token → `RecaptchaService::verify()` returns `false`, as expected — the test secret was the only thing making the earlier check silently pass.

**Frontend `.env` changes need a `dzencode_frontend_site` restart to take effect** — Vite resolves `VITE_*` variables into `import.meta.env` at dev-server-start time, not on every request, so editing `.env` and saving doesn't retroactively update an already-running `npm run dev` process the way a backend `.env` change (read fresh per PHP-FPM request) does.

**Testing implication:** `tests/Feature/Concerns/FakesRecaptcha.php` binds a fake `RecaptchaService` via `$this->app->instance(...)` (same pattern as `FakesRabbitMQService`) rather than `Http::fake()` — Laravel's `Http::fake()` stubs resolve first-match-wins in registration order (`Factory::fake()` appends to a collection, doesn't replace), so a test that needs `success: false` cannot override a `success: true` stub already registered in `setUp()` by calling `Http::fake()` again; swapping the whole service instance doesn't have that problem, since a later `$this->app->instance()` call cleanly replaces the earlier binding. `RecaptchaServiceTest.php` is the exception — it tests `RecaptchaService` itself, so it uses a single `Http::fake()` call per test (no double-registration, no conflict) to assert the real HTTP request shape (token/secret/IP sent correctly) and both success/failure/request-exception outcomes.

## Logging

`LOG_STACK=daily` (was `single` — a single ever-growing `storage/logs/laravel.log`). Laravel's stock `daily` driver only rotates the *filename* by date (`laravel-2026-08-20.log`), still flat in one directory — this project instead wants a folder per month with a file per day inside it, which isn't a built-in Laravel/Monolog option, so the `daily` channel in `config/logging.php` is redefined as `'driver' => 'monolog'` pointing at a custom handler, `App\Logging\MonthlyDailyRotatingHandler` (`app/Logging/MonthlyDailyRotatingHandler.php`) — a `Monolog\Handler\RotatingFileHandler` subclass that overrides `getTimedFilename()`/`getGlobPattern()` to compute `storage/logs/{Y-m}/laravel-{Y-m-d}.log` directly via plain `date()` calls, instead of using Monolog's own `{filename}`/`{date}` template substitution (which can't express "different date granularity for the folder vs. the filename" from a single `dateFormat` — `RotatingFileHandler::setDateFormat()` also hard-validates that format against a `Y`/`Y-m`/`Y-m-d`-shaped regex, so a hand-crafted format string embedding literal path separators isn't an option either). The constructor's `dateFormat`/`filenameFormat` are left at their defaults (`Y-m-d` / `{filename}-{date}`) purely to pass that validation and to keep `RotatingFileHandler`'s own midnight-rollover timing (`getNextRotation()`) working unmodified — they're otherwise unused, since the two overridden methods never reference them.

**Retention is `LOG_DAILY_DAYS=365`** (env name kept from Laravel's stock `daily` driver for familiarity, though it's now passed through as the `maxFiles` constructor arg on the custom handler rather than the driver's own `days` option) — `RotatingFileHandler`'s built-in pruning (glob for existing files via `getGlobPattern()`, sort, delete anything past `maxFiles`) already handles cross-month ordering correctly (a full path like `storage/logs/2025-07/laravel-2025-07-01.log` still lexicographically sorts before `storage/logs/2025-08/...`) and already removes a month folder once its last day-file inside it has been pruned — none of that needed reimplementing, only *where* the files live did. Verified directly (not just read): wrote real fake historical files across three months, ran the handler with a small `maxFiles`, confirmed it kept exactly the newest N files and deleted the now-empty older month directories.

`make logs-laravel` tails today's file directly (`storage/logs/$(date +%Y-%m)/laravel-$(date +%Y-%m-%d).log`) rather than a fixed path, since there's no longer one fixed path to tail. **The `date` computation runs inside `dzencode_app` via `docker exec`, not on the host** — the container is UTC (confirmed: `date.timezone => UTC` in `php -i`, matching the OS clock), so `date` and PHP's own `date()` calls agree there; a host machine in a different timezone (e.g. UTC+3) computing "today" locally can land on a different calendar date than the container did at the moment it actually wrote the file, and the target would tail a file that doesn't exist yet — this happened for real, not hypothetically, once `logs-laravel` shipped.

## Caching

**`App\Services\Resilience\` holds the whole generic circuit-breaker/fallback layer (`ServiceHealth`, `ServiceFallback`, `ResilientCache`, `ReliableQueue`) — separate from `App\Services\CommentService`/`RabbitMQService`, which stay directly under `App\Services\`.** The split is deliberate: everything in `Resilience/` is comment-agnostic and would apply unchanged to any future feature needing the same "try the fast/normal path, degrade gracefully if it's down" behavior, while `CommentService`/`RabbitMQService` are domain/transport-specific and have no reason to move.

**`CACHE_STORE=database`, not `redis`** — this is the app-wide *default* store (used by anything that calls the bare `Cache::` facade with no explicit store: the `throttle` rate limiter, and, as discovered the hard way, Laravel Reverb's own internal restart-check — see § Real-time (backend side) and the incident write-up below). Redis is still used, but only where a feature *explicitly* opts into it via `App\Services\Resilience\ResilientCache` (see below) — it's a deliberately optional performance layer now, never something the app hard-depends on being up. Reach for it on read-heavy, non-personalized endpoints (aggregates, reference/listing data, same response for every visitor) — cache invalidation should hook into model write events (`saved`/`deleted`), not scattered manual calls in controllers/services. Endpoints that are inherently per-user or highly parameterized (search, filtered lists) need a deliberate key strategy — don't cache those by default.

**`App\Services\Resilience\ResilientCache` (singleton, injected into `CommentService`) wraps `remember()`/`many()`/`forever()`/`forget()`/`flushTags()`, trying `Cache::store('redis')` first and falling back to `Cache::store('database')` on any `Throwable`.** A hand-rolled class, not Laravel's built-in `failover` cache driver (`Illuminate\Cache\FailoverStore`, still in `config/cache.php` as the stock `failover` store, just unused by this feature) — the built-in driver was tried first and is a fine general building block, but it has no memory of a failure: every single operation tries every store in order from scratch, unconditionally. On this project's dev host (see the DNS note below) that meant a single `GET comments` — which fires several independent cache operations (a `remember()`'s `get`+`put`, `hydrateRepliesCount()`'s `many()`, any `forever()` warm) — paid Redis's failure cost **on every one of them**, compounding a ~3-4s failure into an observed ~11-12s response.

**Neither the circuit-breaker state nor the try/fallback control flow lives inside `ResilientCache` itself — both are pulled out into their own classes, generic enough to also cover RabbitMQ (see § Queue), not just Redis.** `App\Services\Resilience\ServiceHealth` owns just the state, keyed by an arbitrary service name: `shouldTry(string $service)`/`markUp(string $service)`/`markDown(string $service)`. `App\Services\Resilience\ServiceFallback::attempt(string $service, Closure $primary, Closure $fallback): mixed` owns the control flow: checks `ServiceHealth::shouldTry($service)`, tries `$primary` if worth trying, marks that service up/down, falls back to `$fallback` otherwise. `ResilientCache`'s five methods (`remember`/`many`/`forever`/`forget`/`flushTags`) are thin — each just builds the two closures (one hitting `Cache::store('redis')`, one hitting `Cache::store('database')` or a bare no-op/compute) and hands them to `$this->fallback->attempt('redis', ...)`, rather than each re-implementing the same try/catch/markUp/markDown shape by hand. `App\Services\Resilience\ReliableQueue` (§ Queue) reuses the exact same `ServiceFallback`/`ServiceHealth` pair, once for `'redis'` (job dispatch) and once for `'rabbitmq'` (publish) — **two independent circuits, not one shared flag**, since Redis and RabbitMQ can fail on completely unrelated schedules and a Redis outage saying nothing about RabbitMQ's health (or vice versa) would be a wrong inference. `ServiceHealth::shouldTry($service)` checks a short-TTL flag (`resilient_cache:{$service}_down`) in `Cache::store('database')`; the first failure of a given service writes it via `markDown($service)`, every subsequent call for *that same service* across **any** request or process checks it first and skips straight to the fallback without touching it at all, until it naturally expires and `markUp()`/the next attempt gives it another chance. The flag lives in `database`, not an in-memory/static property, specifically because PHP-FPM tears down the whole application container between requests — an in-process circuit breaker would forget the failure the instant the request ended and pay the full penalty again on the very next one; storing it in the (already-established-as-reliable) `database` cache store makes the "this service is down" knowledge shared across every PHP-FPM worker and every long-running container (`queue`, `outbox`) simultaneously.

**The flag's own TTL isn't a flat 10s — `markDown($service)` backs off the same way `PersistCommentDirectly::backoff()` does, `[10, 30, 60, 120, 300]` seconds, tracked per service via a second counter key (`resilient_cache:{$service}_attempts`, capped at the array's last index once exhausted, reset by `markUp()`).** A flat cooldown meant that spaced-out requests — a comment posted every 15-30s during a real but sparse outage, or just manual testing at a human pace — would each land just *after* the 10s window closed and pay the full connection-timeout cost fresh, over and over, never actually benefiting from the circuit breaker despite it working exactly as designed; the fix isn't to guess a single "right" cooldown, it's to make the cooldown itself grow the longer a service stays down, so it converges toward covering whatever the real request cadence turns out to be. Confirmed live for both services independently: with RabbitMQ down, three requests spaced 12s apart took ~4s / ~4s / ~50ms (the second failure re-armed the circuit at 30s, so the third — 12s later — was still inside it); the same escalation reproduces identically for the `redis` leg via `ReliableQueue::runFallbackJob()` called directly. Measured single-attempt cost: first request after Redis or RabbitMQ disappears ~4s (one failed connection, DNS-bound — see below), every request within the current backoff window near-instant (~50ms), back to normal the moment the service is reachable again and a probe succeeds (`markUp()` resets the counter to zero, so the *next* outage starts back at a 10s cooldown rather than picking up where the last one left off).

**Never cache a raw `Collection` or Eloquent model — always `->toArray()` before returning from a cached closure.** Laravel's `serializable_classes => false` default means a cached object comes back as `__PHP_Incomplete_Class` on the next request.

**Wired up for the comments list, the first cached endpoint — the pattern to repeat for the next one:** `CommentService::getPaginated()` (highly parameterized by `sort_by` × `page`, exactly the case the paragraph above says not to cache by default) calls `$this->cache->remember($key, $ttl, $callback, ['comments_list'])` — cache tags only actually work while the `redis` leg is reachable (`database` doesn't support tags at all), so `ResilientCache::remember()` special-cases a tagged call: if Redis is circuit-broken, it skips the `database` fallback entirely and just calls `$callback()` directly rather than trying (and immediately failing) a tag operation `database` can't do. Each page is cached under `comments:index:{sort_by}:{page}` inside the `comments_list` tag. Only the resolved array (`CommentResource::resolve()` output, plus pagination scalars) is cached, never the `LengthAwarePaginator` object itself — `getPaginated()` rebuilds a fresh `Illuminate\Pagination\LengthAwarePaginator` from the cached array on every call, because `RespondTrait::respondWithJson()` does an `instanceof LengthAwarePaginator` check and calls `->items()`/`->currentPage()`/etc. on it.

**`replies_count` is deliberately kept out of that tagged page cache and out of `withCount('replies')` entirely**, because replying is far more frequent than posting a new top-level comment, and a naive "flush the whole list tag on every create" would mean the list cache almost never survives long enough to be useful. Instead each top-level comment gets its own standalone, untagged, no-TTL (`forever`) counter key `comments:{id}:replies_count`. `CommentService::hydrateRepliesCount()` runs **after** `getPaginated()` pulls its page array out of the tagged cache — on both a hit and a miss, not just on the miss path — because the whole point is that `replies_count` must stay live even while the surrounding page array is still a valid cache hit. It batch-reads the counters for the whole page in one `many()` call, falls back to a single grouped `whereIn('parent_id', ...)->groupBy('parent_id')` count query for any misses, warms those misses back into the cache, then overwrites the `replies_count` key directly on each already-resolved array item (mutates the plain array by reference, since by this point the data has already been through `CommentResource` — there's no Eloquent model left to attach an attribute to). `CommentService::persist()` (the async-created comment's actual DB-write step, see § Queue) branches on `parent_id`: a new top-level comment still flushes the `comments_list` tag (it changes what a page contains) and seeds its own counter to `0`; a new reply does **not** touch the tag at all — it recomputes `Comment::where('parent_id', ...)->count()` and overwrites the parent's counter key directly. Recompute-and-overwrite was chosen over `increment()` specifically so the counter self-heals from any prior drift (lost key, stale seed) instead of compounding it. **The whole cache block in `persist()` is wrapped in its own `try/catch` + `report($e)`, separate from `ResilientCache`'s own internal fallback handling** — see [[feedback-retry-safe-side-effects]]: even a `ResilientCache` failure (both `redis` *and* `database` unreachable, or a genuine bug in this block) must never propagate out of `persist()`, because `persist()` is retried wholesale on failure elsewhere in the pipeline (§ Queue) and `Comment::create()` already succeeded by this point — retrying the whole method would duplicate the comment.

`CommentService::getReplies()` is simpler — no sort/pagination variance, so it's cached under a plain untagged `comments:replies:{comment_id}` key via `$this->cache->remember()` (no tags) and invalidated with `$this->cache->forget()` for that one parent when a reply is created, rather than going through the tag system.

**Incident that drove this whole redesign (2026-08-20): stopping `dzencode_redis` took the entire comments feature down, not just its cache.** Root cause was that `throttle` middleware (gating every comment route) resolved its `RateLimiter` off the app's *default* cache store, which was `CACHE_STORE=redis` — an unreachable Redis threw an uncaught `Predis\Connection\ConnectionException` straight out of `ThrottleRequests`, before the request ever reached `CommentController`. That's also why it looked like "the websockets broke": `POST comments` 500'd at the rate limiter, before `enqueue()`/RabbitMQ/`persist()`/the broadcast ever ran — Reverb/Echo were never actually involved. Separately (and genuinely, confirmed by killing the broker mid-flight and watching it happen), Reverb's own `reverb:start` **does** depend on Redis when `CACHE_STORE=redis` — `Laravel\Reverb\Servers\Reverb\Console\Commands\StartServer::ensureRestartCommandIsRespected()` polls `Cache::get('laravel:reverb:restart')` (the mechanism behind `php artisan reverb:restart`) once at boot and then every 5 seconds for the life of the process — completely unrelated to `REVERB_SCALING_ENABLED` (which stays `false` here and gates a *different* Redis touchpoint, pub/sub for horizontal scaling). Switching the app's default `CACHE_STORE` to `database` fixes both for free, since neither the rate limiter nor Reverb's internal `Cache::` calls specify a store — they just inherit whatever the default is. The `reverb` Docker service also had no `restart:` policy at all (unlike `queue`/`outbox`/`scheduler`), so once it did go down this way it stayed down until someone noticed and restarted it by hand — now fixed with `restart: unless-stopped`, matching the others.

**A residual, environment-specific rough edge affecting only the very first request after Redis disappears, deliberately not chased further:** on Docker Desktop for Windows specifically, a fully-removed `redis` container (i.e. `docker stop`, not just an unresponsive process) makes `getaddrinfo("redis")` itself take ~3-4 seconds to fail (confirmed with a throwaway container outside the compose stack, with and without a tightened `resolv.conf options timeout:1 attempts:1` — made no measurable difference, so this lives inside Docker Desktop's embedded resolver, not something `resolv.conf`/Predis-level config can bound). `ResilientCache`'s circuit breaker means this DNS penalty is now paid **once** (by whichever request first discovers the failure), not once per cache operation per request — but that first ~4s is unavoidable on this host OS specifically. A **reachable-but-unresponsive** Redis (the more realistic prod failure: process crash, OOM, overload) never hits this path at all — it's bounded fast by `config/database.php`'s `timeout`/`read_write_timeout: 1` on the `cache` Redis connection (`max_retries: 0` there too, since retrying before falling back just delays what `ResilientCache` already provides). Flagged so a ~4s first request during a `docker stop dzencode_redis` test on Windows isn't mistaken for the circuit breaker not working.

## Queue (RabbitMQ, with a Laravel-job fallback/retry path)

Comment creation (`POST comments`) is async, deliberately built on **raw `php-amqplib` for the actual message broker, not a Laravel queue driver pointed at RabbitMQ** (e.g. `vladimir-yuldashev/laravel-queue-rabbitmq`) — full manual control over publish/consume rather than a `Queue::extend('rabbitmq', ...)` connector.

**No outbox hop — `enqueue()` publishes to RabbitMQ synchronously, in the request, with a fallback onto a plain Laravel job.** An earlier version of this pipeline dispatched a `PublishCommentToRabbitMQ` job onto a Redis-backed "outbox" queue first, so a request never touched RabbitMQ directly — measured overhead of that extra hop turned out to be only a few ms on the median case, at the cost of an occasional 800ms–1s tail-latency spike from two independent queue systems' wake-up paths stacking (Laravel's `BLPOP` wait, then AMQP's own `channel->wait()` loop). Simplified instead: `CommentController::store()` → `CommentService::enqueue(array $data)` sanitizes the text via `sanitizeBody()` (**before** publish — so raw unsanitized HTML, a live XSS payload, is never the thing sitting at rest in a RabbitMQ message or a Job payload) then calls `App\Services\Resilience\ReliableQueue::send('comments_create', $data)`.

**`App\Services\Resilience\ReliableQueue` is a generic, comment-agnostic "publish to this queue, falling back to a Laravel job if that fails" service — not comment-specific logic living inside `CommentService`.** `send(string $queue, array $data)` wraps `RabbitMQService::publish($queue, $data)` in `ServiceFallback::attempt('rabbitmq', ...)` (see § Caching); on failure it falls back to `runFallbackJob($queue, $data)`, which looks up which job class to fall back to via `config("reliable_queue.fallback_jobs.{$queue}")` (`config/reliable_queue.php` — a dedicated config file, not bolted onto `config/rabbitmq.php`, since this mapping is about jobs/reliability, not RabbitMQ specifically) rather than a hardcoded class name, so any future queue just needs one config line, not new service code. **Throws a `RuntimeException` immediately if a queue has no configured fallback job** — a misconfigured queue should fail loud at the point of the bug, not silently swallow the message or crash with a cryptic "call to a member function `dispatch()` on null." Both call sites end up going through `runFallbackJob()`: `CommentService::enqueue()` via `send()`'s own fallback, and `App\Console\Commands\ConsumeCommentsQueue`'s handler calls it directly (no publish step needed there — see below) when `CommentService::persist()` throws after RabbitMQ already delivered the message.

**Wrapping the RabbitMQ publish itself in the `rabbitmq`-keyed circuit breaker (not just an inline `try/catch`) was a fix made after catching the gap live: without it, every single request paid RabbitMQ's own connection-timeout cost, even once Redis's circuit was already open.** Measured with both RabbitMQ and Redis down at once: first request ~7.9s (RabbitMQ's ~4s connection attempt, then — since that circuit wasn't open yet either — Redis's ~4s connection attempt inside `runFallbackJob()`); before this fix, every *subsequent* request still cost ~3.9s (RabbitMQ's timeout alone, paid fresh every time, since only the Redis leg had a circuit breaker); after wrapping `publish()` the same way, subsequent requests dropped to ~50-70ms, and both circuits reset independently once each service actually recovers.

**`runFallbackJob()` uses `App\Services\Resilience\ServiceFallback::attempt('redis', Closure $primary, Closure $fallback): mixed` to decide between dispatching the job for real and running it synchronously right there.** `$primary` dispatches the resolved job class (`$jobClass::dispatch($data)`) onto Laravel's own `redis`-connection queue; `$fallback` runs that **same job's `handle()` directly**, bypassing the queue entirely, via `app()->call([new $jobClass($data), 'handle'])` — Laravel's container resolves `handle()`'s type-hinted parameters (e.g. `CommentService $commentService`) from the container exactly as it would for a real queued invocation, so this works for any job following the standard `__construct($data)`/`handle(Dependency $x)` shape, not just this one. `ServiceFallback::attempt()` is what decides *which* of the two closures actually runs: skips straight to `$fallback` if the `redis` circuit is already open, otherwise tries `$primary` and only falls back if that throws.

**A sharp edge that bit this exact code once, worth flagging permanently: never let a closure passed to `ServiceFallback::attempt()` return a Laravel `PendingDispatch`.** `SomeJob::dispatch($data)` doesn't push to the queue at the point it's called — it returns a `PendingDispatch` object, and the actual `Queue::push()` happens in that object's `__destruct()`, whenever PHP's refcounting decides to collect it. The first version of `runFallbackJob()` wrote `fn () => $jobClass::dispatch($data)` — an arrow function implicitly *returns* the `PendingDispatch`, which then got returned again from `attempt()`'s `try` block up through `return $value`, past the `try/catch` boundary entirely, and only got destructed (triggering the real, fallible `Queue::push()`) *after* `attempt()` had already returned control to its caller — so a Redis failure at that point threw a completely unhandled exception straight through to a `500`, exactly the failure mode this whole mechanism exists to prevent. Confirmed live: with Redis stopped, the bug reproduced as an uncaught `Predis\Connection\ConnectionException` with `PendingDispatch->__destruct()` sitting in the middle of the stack trace. Fixed by not returning the dispatch call's result at all — `function () use ($jobClass, $data) { $jobClass::dispatch($data); }` — so the `PendingDispatch` temporary is destructed (and the real push attempted) as the last thing that happens *inside* the closure body, while still inside `attempt()`'s `try`. Any future `Closure` wrapping a bare `::dispatch()` call anywhere in this codebase needs the same treatment — don't let the closure return what `dispatch()` returns.

**`QUEUE_CONNECTION=redis`, not the framework-default `database`** — measured, not assumed: dispatching a comment carrying a ~1.5MB base64 image (a realistic photo upload) took **974ms** with the `database` driver against **26ms** with `redis` (direct `RabbitMQService::publish()`, for comparison, is ~13ms). The gap is a synchronous `INSERT` with a commit-time `fsync` for a multi-megabyte row versus an in-memory Redis `RPUSH` — on Docker Desktop for Windows specifically the MySQL side is much worse than on native Linux disk I/O, but the ordering holds regardless of host OS. Since `redis` normally trades some durability for that speed (an unflushed in-memory value lost on a crash), `docker-compose.yml`'s `redis` service runs `redis-server --appendonly yes` with its own named volume, `redis_data:/data` — so a queued-but-not-yet-processed `PersistCommentDirectly` job survives a Redis container restart the same way it would with the `database` driver, just without the `fsync`-per-row cost.

`App\Services\RabbitMQService` is a thin, comment-agnostic wrapper around `PhpAmqpLib\Connection\AMQPStreamConnection` (`config/rabbitmq.php` holds host/port/user/password/vhost/queue-name from env) — `publish()` declares a durable queue and sends a persistent (`delivery_mode: 2`) JSON message; `consume()` declares the same queue, sets `basic_qos(prefetch: 1)`, and runs a blocking `$channel->wait()` loop, `ack()`-ing on a successful handler call and `nack(requeue: false)` + `report($e)` on a thrown exception. **It connects lazily** — the connection/channel open on first `publish()`/`consume()` call, not in the constructor — otherwise `CommentService`/`RabbitMQService` being constructor-injected into `CommentController` would attempt a connection during controller resolution, before any calling code has a chance to handle a failure.

`App\Console\Commands\ConsumeCommentsQueue` (`php artisan comments:consume`) is the RabbitMQ consumer entrypoint — a long-running command, not a one-shot job, run by the `queue` Docker service (`_docker/app/queue-entrypoint.sh`, same wait-for-`vendor/autoload.php` pattern as `scheduler-entrypoint.sh`/`reverb-entrypoint.sh`) with `restart: unless-stopped` as its crash-recovery mechanism (no in-process reconnect loop). Its handler wraps `CommentService::persist($payload)` in its own `try/catch`: on success it returns normally so `RabbitMQService::consume()` acks the message; on failure it `report()`s the exception and calls `ReliableQueue::runFallbackJob('comments_create', $payload)` **instead of letting the exception propagate** — which still means the handler returns normally and the message still gets acked. This is deliberate: responsibility for retrying has been handed off to Laravel's queue (with `PersistCommentDirectly`'s `$tries`/`backoff()`), so there's no reason for the message to sit around unacked in RabbitMQ or to rely on `RabbitMQService::consume()`'s own `nack(requeue: false)`, which has no backoff or dead-letter exchange behind it — a message that got `nack`'d without this handoff would just be logged and dropped, permanently.

**Why `persist()` itself only guards its non-critical side effects, not the whole method, with try/catch:** `persist()` does exactly two authoritative DB writes — `Contact::firstOrCreate()` (see the `contacts`/`Comment::contact()` note under § Current state above) and `Comment::create()` (including base64 image decode/re-encode via `storeImage()`/`SavesBase64Images` — this still runs inside whichever caller invoked `persist()`, so raw base64 image payloads do ride through both a queued job and the AMQP message body; image bytes get re-encoded through GD regardless before ever reaching disk, so there's no equivalent stored-XSS-style risk to defer against the way there is for `text`). Both writes are wrapped together in one `DB::transaction()` — if `Comment::create()` throws after `Contact::firstOrCreate()` already inserted a brand-new contact row, the transaction rolls that insert back too, so a retry starts from a clean slate instead of leaving an orphaned, comment-less `Contact` behind (harmless either way since `firstOrCreate()` would just reuse it, but there's no reason to leave it). The transaction is left **unguarded** by any try/catch — if it throws, the exception is meant to propagate to the caller (`ConsumeCommentsQueue` or `PersistCommentDirectly::handle()`) so the retry/fallback machinery above kicks in; nothing was written, so retrying is safe. The `Cache::tags()`/`replies_count` bookkeeping and `CommentCreated::dispatch()` (broadcast) that follow are each wrapped in their **own** `try/catch` + `report($e)` instead — deliberately *not* allowed to propagate, because by the time they run the comment row already exists. If a Redis hiccup or an unreachable Reverb caused the whole method to fail and get retried, the retry would call `Comment::create()` again and produce a duplicate comment; treating cache/broadcast as best-effort avoids that, at the cost of a stale list-cache page (self-heals at the 3600s TTL) or a missed live-update (visible on the next full list load) in the rare case one of them actually fails. `persist()` no longer calls `sanitizeBody()` itself — it trusts `$data['text']` is already sanitized by the time it gets there.

`POST comments` returns `202` + `{"status": "queued"}` immediately, never the created comment — the frontend already doesn't read the POST response (it only ever inserts a new comment via the `.comment.created` Echo broadcast, see § Real-time), so this required no frontend change.

**Known eventual-consistency edge case:** `CommentRequest`'s `parent_id`/`replied_to_comment_id` existence checks run against the DB at request time — a reply referencing a parent comment that was itself just submitted (and not yet actually persisted) will fail validation until that parent comment exists. Not worked around — flagged here so it isn't mistaken for a bug.

**`docker-compose.yml`'s `rabbitmq` service has its own named volume, `rabbitmq_data:/var/lib/rabbitmq`** (alongside `db_data`) — RabbitMQ's on-disk message store (durable queues + `delivery_mode: persistent` messages) otherwise lives in the container's writable layer and would survive a plain `docker restart` but not a `docker compose down`/recreate. **The service also pins `hostname: dzencode_rabbitmq`** — RabbitMQ's node identity is `rabbit@<hostname>`, and without a fixed hostname Docker assigns a new random one to every recreated container, so the volume's data would end up orphaned under the old node name instead of picked back up (confirmed by hitting exactly this while testing the volume — omitting the pinned hostname is the one way to make this volume silently useless).

**The `rabbitmq` service only publishes `5672` (AMQP, needed by `queue`/`outbox`, always on)** — the `-management` image variant still runs the HTTP management plugin *inside* the container regardless, but nothing publishes `15672` to the host by default, so it's unreachable unless asked for. It's still the same image (switching to plain `rabbitmq:3-alpine` would need `rabbitmq-diagnostics`-only compatible tooling and buys little), just not exposed. `make rabbitmq-ui` starts a separate one-purpose `dzencode_rabbitmq_ui` container (`alpine/socat`, `profiles: [rabbitmq-ui]` in `docker-compose.override.yml`) that does nothing but forward host `15672` → `rabbitmq:15672` over the compose network — the same "small standalone container reaching an always-on backend service" shape as `phpmyadmin`/`db`, chosen specifically because Compose `profiles:` gate an entire service, not one port on an already-running one, so there was no way to make *only* the UI port optional on the `rabbitmq` service itself. Since `docker-compose.override.yml` is never loaded by `make prod` (`-f docker-compose.yml -f docker-compose.prod.yml` only), this also means the management UI can't accidentally end up reachable in production.

**Testing implication:** `tests/Feature/Concerns/FakesRabbitMQService.php` binds a fake `RabbitMQService` (records to `$published` instead of touching a real broker) — every test exercising `store()`'s happy path needs it in `setUp()`, otherwise a real publish attempt happens under the default `sync` test queue driver. `CommentQueueTest::test_store_falls_back_to_a_direct_job_when_the_broker_is_unreachable()` binds a `RabbitMQService` subclass whose `publish()` always throws, then asserts (via `Queue::fake()` + `Queue::assertPushed()`) that `PersistCommentDirectly` gets pushed instead — no real Redis integration/cleanup needed for this anymore, since the fallback is just a normal fakeable `Queue::dispatch()` call now (unlike the old outbox job, which needed a real `dzencode_redis` round-trip to prove the dispatch survived a `sync`-mode test environment).

**Two follow-up performance fixes made to `RabbitMQService` while it still lived inside a dedicated outbox job — still relevant since `RabbitMQService` is a singleton used by both the request path and the `queue` consumer:**

1. **`RabbitMQService` is bound as a singleton** (`AppServiceProvider::register()`) instead of the default fresh-instance-per-resolution — `dzencode_queue`'s `comments:consume` is one long-running process handling many messages over its lifetime, and without a singleton binding every resolution got its own brand-new `AMQPStreamConnection` (full TCP + AMQP handshake) even though `RabbitMQService` connects lazily. Measured: per-message time dropped from a bimodal ~4ms/~110ms (fast normally, slow — connection-handshake-dominated — occasionally) down to consistently sub-2ms once the connection is warm. **This introduced a real correctness risk that had to be fixed alongside it**: a singleton means a dead connection (broker restarted mid-flight) stays cached, so any retry would keep reusing the *same* broken channel and fail identically instead of self-healing — unlike a fresh-connection-per-call, which incidentally self-heals for free. `RabbitMQService::publish()` now catches `Throwable`, resets `$channel`/`$connection` back to `null`, and rethrows — so the *next* attempt reconnects from scratch. Verified live: killed the broker mid-flight, confirmed a call failed against the stale singleton connection, confirmed a later call reconnected and succeeded once the broker was back.
2. **`config/queue.php`'s `redis` connection sets `'block_for' => (int) env('REDIS_QUEUE_BLOCK_FOR', 5)`** (was `null`) — `null` means `queue:work` does a non-blocking `LPOP`/`RPOP` and, finding nothing, sleeps for `--sleep` (default 3s) before checking again, so a `PersistCommentDirectly` job dispatched right after a poll could sit for up to ~3s before being picked up. `block_for` switches this to a Redis `BLPOP` with that many seconds as the block timeout — the worker wakes up the instant a job is pushed instead of waiting for its next poll. Measured: pickup went from "up to ~3s, timing-dependent" to landing in the same wall-clock second as the dispatch in every trial.

**Image size still genuinely affects `publish()`'s own runtime, and that's expected, not a bug to chase further** — `basic_publish()` cost scales with payload size, since the full base64 image rides in the AMQP message body (deliberately — the image is decoded/re-encoded inside `persist()`, not before publish). Measured: ~4ms text-only vs. ~52ms for a ~1.5MB image payload on an otherwise-warm connection. This is the AMQP write itself taking longer for more bytes — reducing it further would mean revisiting whether the raw image belongs in the queue message at all, which is a bigger design conversation than a performance tweak.

## Tests

Ship tests with the API code that needs them — adding/changing an endpoint means adding/updating its feature test in the same change, and if a request/response contract changes, the existing test for it gets updated alongside, not left asserting the old shape. Match the existing `tests/Unit/ExampleTest.php` / `tests/Feature/ExampleTest.php` style: class-based (`class XTest extends TestCase { use RefreshDatabase; public function test_snake_case_description(): void { ... } }`), not Pest's functional `it()`/`test()` style.

**`tests/TestCase.php`'s `setUp()` flushes `Cache::store('redis')` before every test.** Needed once `CommentService` started calling `App\Services\Resilience\ResilientCache` explicitly (see § Caching) instead of the bare `Cache::` facade — `phpunit.xml`'s `CACHE_STORE=array` override no longer isolates comment-cache tests from each other, because `ResilientCache`'s `redis` leg is a *real* Redis connection (`REDIS_DB=5`), which — unlike Laravel's `array` store — isn't torn down when the framework rebuilds the application container between tests. Without this, a `replies_count` (or similar `forever()`-cached) key written by one test could leak into the next test that happens to reuse the same comment id, causing order-dependent failures. This mirrors what `RefreshDatabase` already does for the DB, just for the one cache backend that isn't process-scoped. It does **not** need to also clear the circuit-breaker's `resilient_cache:redis_down` flag — that lives on the `database` cache store, which `RefreshDatabase` already wipes per test.

**The comment test suite is split across several `tests/Feature/*Test.php` files by concern, not one growing `CommentControllerTest.php`** — split out once that single file passed ~40 tests and mixed unrelated concerns (HTTP contract, queue dispatch, rate limiting, the job itself, service-level persistence, pure string sanitization) badly enough that finding a specific test meant scrolling, not searching. Current split, treat as the pattern for the next feature that grows this large:
- `CommentControllerTest.php` — the `index`/`replies`/`store` HTTP contract itself: response shapes, cache-reflects-after-write, `store`'s validation edge cases (422s) and the two happy-path 202s. No queue/rate-limit/job internals.
- `CommentQueueTest.php` — `store`'s publish-or-fallback behavior: publishes to RabbitMQ and returns `202` on the happy path, falls back to dispatching `PersistCommentDirectly` (`Queue::fake()` + `Queue::assertPushed()`) and still returns `202` when the broker is unreachable (see § Queue), text gets sanitized before it ever reaches either payload.
- `CommentRateLimitTest.php` — the `throttle` limits on `store`/`index`, one test per route.
- `PersistCommentDirectlyTest.php` — the fallback/retry job in isolation: `handle()` actually persists the comment (it's a thin wrapper around `CommentService::persist()`, so this needs `RefreshDatabase`, unlike the old publish-only job's test), `$tries`/`backoff()` are configured as expected.
- `ServiceFallbackTest.php` — `ServiceFallback::attempt()` in isolation with plain closures (no real queue/Redis/RabbitMQ involved): returns the `$primary` result on success, returns the `$fallback` result when `$primary` throws, skips `$primary` entirely once `ServiceHealth::markDown()` has already opened that service's circuit, and confirms two different service names (`'redis'`/`'rabbitmq'`) are tracked independently.
- `ServiceHealthTest.php` — `ServiceHealth`'s backoff itself, asserted against the `cache` table's own `expiration` column (there's no public "remaining TTL" getter): repeated `markDown()` calls for the same service produce a strictly increasing `expiration` each time (`[10, 30, 60, 120, 300]`), and `markUp()` resets the next `markDown()` back to the first (10s) step instead of continuing the escalation.
- `RecaptchaServiceTest.php` — `RecaptchaService::verify()` against a real `Http::fake()`'d `siteverify` response: returns `true`/`false` matching Google's `success` field, returns `false` (fails closed) when the HTTP call itself errors, and sends the token/secret/IP in the expected shape.
- `ReliableQueueTest.php` — `ReliableQueue::send()`/`runFallbackJob()` against a faked `RabbitMQService` (`FakesRabbitMQService` trait) and `Queue::fake()`: publishes and never touches the fallback job on the happy path, falls back to the configured job (`PersistCommentDirectly`, resolved from `config('reliable_queue.fallback_jobs')`) when publish fails, throws for a queue with no configured fallback job, skips the publish attempt entirely once the `rabbitmq` circuit is already open, and — this is the one test in the suite that exists specifically because a fake queue can't catch the `PendingDispatch::__destruct()` pitfall described in § Queue — runs the job's `handle()` synchronously (asserted via `assertDatabaseHas`, not `Queue::assertPushed`) once the `redis` circuit is already open.
- `CommentServiceTest.php` — `CommentService::persist()` called directly (bypassing the queue and RabbitMQ, since this is what both the consumer and `PersistCommentDirectly` actually call): DB writes, SQL-injection-as-literal-data, base64 image storage/downscaling, rejecting a disguised non-image.
- `CommentSanitizeBodyTest.php` — `CommentService::sanitizeBody()` called directly: XSS-stripping, link `rel` injection, line-break/whitespace preservation. Pure string-in-string-out, no `RefreshDatabase` needed.

`tests/Feature/Concerns/FakesRabbitMQService.php` is a shared trait (`fakeRabbitMQService()`, binds an anonymous `RabbitMQService` subclass that records to a public `$published` array instead of touching a real broker) — every test class that exercises `store()`'s happy path needs it in `setUp()` (even a 422-only test file would be safe without it, but anything that can reach `202` under the default `sync` test queue driver will actually attempt a real publish if it isn't faked, since `enqueue()` now calls `RabbitMQService::publish()` directly instead of going through a job).

Dedicated security-test categories (kept from the original file, not new to the split): XSS payloads (`<script>`, event-handler attrs, `javascript:` hrefs) asserted stripped from stored output, and SQL-injection payloads asserted stored as literal data (not executed) via `assertDatabaseHas` + `Schema::hasTable()` still returning true afterward. New user-generated-content endpoints should get the same two categories of test, not just happy-path/validation coverage. Don't write literal exploit strings as test fixtures when a benign non-image/non-script string proves the same thing just as well (e.g. testing "invalid image data is rejected" needs *any* non-image bytes, not a PHP webshell one-liner) — a real exploit signature committed to a file gets flagged by antivirus scanners even though it's inert, and even after removing it from the working tree, this harness's own file-history snapshots can retain the old version, so the string keeps getting flagged until those are found and purged too.

## Real-time (backend side)

See root `CLAUDE.md` § Real-time for the full picture (Reverb + Echo, per spec — not a custom Redis/`ws` relay, which is what this project actually started with and later replaced). Wired up for comments: `CommentService::persist()` (run from inside either the RabbitMQ consumer or the `PersistCommentDirectly` fallback job, see § Queue — never from the HTTP request itself) dispatches `App\Events\CommentCreated`, which implements `ShouldBroadcastNow` and defines `broadcastOn()`/`broadcastAs()`/`broadcastWith()` — no separate Listener class, Laravel's broadcasting integration handles `ShouldBroadcast*` events automatically once dispatched. `ShouldBroadcastNow`, not `ShouldBroadcast` — the latter queues the broadcast job onto Laravel's own queue system, and this project has no Laravel queue worker consuming broadcast jobs (`scheduler`'s container runs `schedule:work`, and the new `queue` container runs a custom RabbitMQ consumer, not Laravel's `queue:work`), so a queued broadcast would just sit in the `jobs` table forever and never actually reach a client. `config/broadcasting.php` and `config/reverb.php` were published via `php artisan reverb:install` (composer package `laravel/reverb`). `routes/channels.php` is empty — no private/presence channel auth exists (no `App\Models\User` in this project at all) — design real auth there before broadcasting anything user-specific over a channel a Comment-like anonymous feature doesn't need.
